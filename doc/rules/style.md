# TaskMate Coding Style

This guide documents the style used in the TaskMate codebase, excluding
`srcs/autoCode/` and generated sections. It complements the existing
`.clang-format`, `.clang-tidy`, architecture rules, and prefix rules.

## Formatting

- Use the project `.clang-format` file as the source of truth for C and header
  formatting.
- Indent with tabs. Tab width and indentation width are both 4.
- Use Allman braces:

```c
if( condition )
{
	doWork();
}
```

- Keep the project spacing style around control statements:
  `if( condition )`, `for( ... )`, `while( ... )`.
- Short simple bodies may stay on one line when this improves readability:

```c
if( value == 0 ) { return ERR_NO_ERROR; }
```

- Keep lines at or below 100 columns.
- Use right-aligned pointer stars:

```c
const tm_string_t *name;
mod_thread_item_t *thread;
```

- Prefer explicit parentheses in conditions and macros when operator precedence
  could be unclear.

## File Structure

- Start C, header, AWK, and Makefile fragments with the TaskMate BSD-2-Clause
  license banner used in `doc/licence_header.txt`.
- Add a Doxygen file block after the license banner in C and header files:

```c
/**
 * @file module.c
 * @brief module implementation.
 */
```

- Include the matching local header first in `.c` files.
- After the matching header, include system headers before project headers.
- Let clang-format sort include blocks.
- Keep headers guarded with an uppercase path-based guard:

```c
#ifndef SYSCORE_MODULES_H
#define SYSCORE_MODULES_H

...

#endif // SYSCORE_MODULES_H
```

## Naming

- Use the established TaskMate prefixes only when they describe a real boundary
  or subsystem. Follow `doc/rules/TaskMate_prefixes.md`.
- Current important prefixes:
  `tm_`, `DRV_`, `sc_`, `gpio_`, `err_`, `mod_` / `MOD_`, and `rl_`.
- Public subsystem APIs use lower camel case after the prefix:

```c
void mod_threadSetCurrent(uint8_t n);
bool sc_gpio_signalGet(gpio_signal_t signal);
```

- Types use snake case with a `_t` suffix:

```c
typedef struct
{
	...
} mod_thread_item_t;
```

- Enum constants and preprocessor constants use uppercase snake case:

```c
GPIO_PIN_MODE_OUTPUT_PP
MOD_CANARY
```

- Static file-local data uses descriptive snake case:

```c
static rl_data_base_t to_run;
static const hal_port_t mcu_ports[PORT_COUNT];
```

- Makefile variables use semantic uppercase prefixes. Follow
  `doc/rules/make_variable_prefixes.md`: `PATH_`, `PATHS_`, `FILE_`, `FILES_`,
  `VAL_`, `OPT_`, `COLOUR_`, and `CFLAGS_...`.

## C Design Rules

- Prefer explicit fixed-width integer types from `<stdint.h>` for embedded data.
- Use `bool` from `<stdbool.h>` for boolean state.
- Keep hardware-specific code inside HAL architecture, MCU, or board directories.
- Keep portable contracts in `srcs/interfaces/`; they must not depend on HAL,
  sysCall, services, or tasks.
- Tasks should use sysCall and service APIs, not raw HAL or MCU registers.
- Keep module state private with `static` file-local storage unless it is part of
  an intentional public interface.
- Prefer small focused functions over large mixed-responsibility functions.
- Avoid magic numbers in hand-written code. Use named constants or document why a
  literal is required. Generated code may require local `NOLINT` exceptions.
- Use explicit null or zero checks when this makes intent clearer.
- For register macros and bit manipulation, fully parenthesize macro parameters
  and results.

## Comments

- Comments should explain intent, constraints, hardware behaviour, timing, or
  non-obvious ordering.
- Do not repeat what the code already states.
- Use short section comments for groups of declarations when it improves scanning:

```c
/*
 * Modules functions
 */
```

- Use inline comments sparingly for compact hardware meanings or guard names:

```c
GPIO_PIN_MODE_OUTPUT_PP, // push-pull
#endif // INTERFACES_GPIO_COMMON_H
```

## Generated Code

- Do not manually edit generated regions.
- Generated regions are marked with autoCode tags and clang-format fences:

```c
// [autoCode_tag] name
// clang-format off
/*
 * do not edit code between tag
 * code generated by autoCode, any change will be lost
 */
...
// clang-format on
// [/tag]
```

- If generated code requires clang-tidy suppression, scope `NOLINTBEGIN` and
  `NOLINTEND` narrowly around the generated or diagnostic-heavy area.

## Build Scripts And AWK

- Keep BSD license banners on Makefile fragments and AWK scripts.
- Use uppercase semantic Make variables and `${VAR}` expansion consistently.
- Prefix shell commands in make recipes with `@` when command echoing would add
  noise to normal build output.
- Use aligned, readable `printf` output for build summaries and diagnostics.
- In AWK scripts, keep parser state explicit with named state variables and
  small helper functions such as `trim()`, `error()`, and `error_end()`.

## Tooling

- Run clang-format before committing C or header changes.
- Keep clang-tidy warnings actionable; use local suppressions only for deliberate
  exceptions.
- Do not introduce new style rules that conflict with `.clang-format`,
  `.clang-tidy`, or the existing architecture and interface rules.
